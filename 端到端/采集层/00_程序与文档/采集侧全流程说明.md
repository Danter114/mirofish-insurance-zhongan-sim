# 采集侧全流程说明

- **我的模块**：采集侧（整条链的最上游）
- **我的上游**：无软件上游 —— 数据来自 6 类公开舆情渠道（微博 / 抖音 / 小红书 / 新闻门户 / 黑猫投诉 / 监管通报），由人工 + AI 辅助检索取得
- **我的下游**：知识图谱侧（GraphRAG 上游包），我给它的东西是每个事件一份的 `eventN.json`（28 字段事件包）；另有舆情看板 HTML 作为展示交付物

---

## 一、这份文档是什么

采集侧做两件事：**把真实世界里的舆情帖子采回来**（原始数据 raw，21 字段），**把它们变成下游能直接用的标准事件包**（processed，28 字段），并顺手产出一份人看的舆情看板。整条链上（采集 → 图谱 → 桥 → 仿真 → 报告），本模块是第一段，只负责"数据从哪来、长什么样"，不建图、不推演、不预测。

**配套材料清单**（均在桌面 `众安舆情_事件1至13_数据包\` 内，路径以此为根）：

| 材料 | 位置 | 作用 |
| --- | --- | --- |
| `build_event.py` | 根目录 | 通用处理程序：raw → processed（规则判定 + LLM 标注） |
| `使用说明.md` | 根目录 | 文件说明 + 看板复现规则（字段格式的权威定义） |
| `00_程序与文档\看板生成\evt_dash_builder.py` | 程序与文档 | 看板生成器：processed + 文案包 → 单文件 HTML |
| `00_程序与文档\看板生成\evt_packs\` | 程序与文档 | 12 个事件的看板文案包（叙事层内容） |
| `00_程序与文档\采集规则.md` | 程序与文档 | raw 21 字段采集规则（6 渠道口径、过滤规则、采集流程） |
| `00_程序与文档\舆情事件分类体系.md` | 程序与文档 | 事件类型 8 类枚举（event_type 校验依据） |
| `EVT-001_…` ~ `EVT-013_…` | 13 个事件目录 | 每事件 raw / processed / 看板 各一份（共 105 条） |
| 桌面 `采集规则.md` | 桌面 | raw 21 字段采集口径（渠道、窗口、过滤规则） |
| 桌面 `舆情事件分类体系.md` | 桌面 | 事件六大类 + 10 个扩展类型 |
| 桌面 `众安舆情_事件1至13_数据改动明细.md` | 桌面 | 事件 1-12 从参考包转入时的全部改动 |

**三类读者只读这些节就够：**

- 评委 / 命题方：第二节（一分钟版本）、第五节（关键决策）、第八节（验收结果）
- 下游图谱侧对接人：第三节（交界，重点）、第四节、第六节
- 新接手的人：第一节到第四节通读，其余按需

## 二、一分钟版本

对每个事件：先在参数卡上定死"事件号、两天窗口（Day0-Day1）、主体与产品名、检索词、排除词"，然后只在 6 类渠道里逐平台检索公开帖子，按三层过滤（窗口 + 关键词硬规则、LLM 相关性二分类、垃圾信息 8 类清单）留下确认相关集合，逐条核对原文并把正文全文存入快照，组装成 21 字段 raw；随后用通用程序 `build_event.py` 处理：角色（监管/媒体/KOL）按作者名与粉丝数规则判定、客户与网民由 LLM 判定、情感与主题与实体由 LLM 标注（温度 0，失败重试 2 次、兜底词表），输出 28 字段 processed；最后把 processed 交给下游图谱侧，同时用生成器 + 文案包产出一份 7 模块的舆情看板 HTML。

```
公开舆情源（6 渠道，无软件上游）
   │ 人工 + AI 辅助检索（参数卡：Day0-Day1 窗口 / 关键词 / 排除词）
   ▼
raw（21 字段原始采集，含正文全文与原文快照）
   │ build_event.py（规则判定角色 + LLM 标注情感/主题/实体）
   ▼
processed（28 字段事件包）──────────→ 舆情看板 HTML（7 模块，单文件）
   │
   ▼
下游知识图谱侧（建图 / 定槽位 / 选人）
```

**调不调大模型**：采集与结构化阶段不调；标注阶段调 DeepSeek（`deepseek-v4-flash`，温度 0）。**联不联网**：采集阶段需联网访问公开页面（历史事件已由人工完成并留快照）；处理与看板阶段不联网。**依赖**：Python 3.10+、requests 包；看板 HTML 零外部依赖。

## 三、交界

### （1）上游给我什么 / 我给下游什么

**上游**：无软件模块。数据源是真实平台公开页面，采集时逐帖记录：

| 项 | 类型 | 取值范围 | 谁产 | 缺了会怎样 |
| --- | --- | --- | --- | --- |
| channel | 字符串 | 6 类枚举之一 | 人工判定 | 缺失则帖子无法归类，直接丢弃 |
| post_url | 字符串 | 有效原帖详情页链接，可为空串 | 人工记录 | 为空则无法回溯核验，明细表显示"—"；采集侧允许但降级 |
| content | 字符串 | 正文全文（不写摘要） | 人工复制 | 缺失丢弃（后续一切标注无从谈起） |
| publish_time | 字符串 | `YYYY-MM-DD HH:MM` | 人工记录 | 缺失丢弃（窗口判定与 timespan_days 依赖它） |
| author_name | 字符串 | 昵称/媒体名/机构名 | 人工记录 | 缺失则角色判定失效，下游 5 字段校验直接拒绝 |

其余 16 个 raw 字段（post_id、title、source_platform、event_type、author_uid、author_fans、author_ip_location、like/comment/repost/collect_cnt、is_repost、keyword_match、topic_tag、topic_list、capture_date）有则记、无则留空，不臆造。完整定义见《使用说明.md》2.1 节。

**下游**：知识图谱侧。交付物 = `EVT-00N_processed.json`（28 字段 JSON 数组），逐字段：

| 字段 | 类型 | 取值范围 | 谁产 | 缺了会怎样 |
| --- | --- | --- | --- | --- |
| post_id | str | `EV{号}_{平台缩写}_{3位序号}` 全局唯一 | 采集侧 | 下游入口校验缺失即拒 |
| content | str | 正文全文 | 采集侧 | 同上，缺失即拒 |
| channel | str | 6 类枚举 | 采集侧 | 同上，缺失即拒 |
| publish_time | str | `YYYY-MM-DD HH:MM` | 采集侧 | 同上，缺失即拒 |
| author_name | str | 昵称/媒体名 | 采集侧 | 同上，缺失即拒 |
| event_id | int | 1~13 | 程序参数 | 缺失时下游按"NA"事件归组，口径错乱 |
| role_type | str | 监管/媒体/KOL/客户/网民 | 规则 + LLM | 缺失时下游按渠道/昵称兜底推断，准确性降级 |
| sentiment | str | 正面/中性/负面 | LLM（兜底词表） | 缺失时下游 stance 推断失去输入 |
| topic_hit / extract_entity | list[str] | 主题词/实体名列表 | LLM | 缺失时下游"兴趣匹配"与实体提取塌掉 |
| timespan_days | int | 0~1 | 程序硬算 | 缺失时下游窗口划分失效 |
| is_origin | bool | false=转载 | 程序取反 | 缺失时下游传播链分析失效 |
| event_t0 | str | `YYYY-MM-DD` | 参数 | 缺失时下游以最早帖时间兜底 |
| topic_tag / topic_list | str / list | 事件级同值 | 参数/raw | 缺失时下游相关性计算缺输入 |
| capture_date | str | `YYYY-MM-DD` | 采集侧 | 仅存档用途 |
| source_platform / event_type | str | 平台名 / 8 类枚举之一 | 采集侧 | 下游不读，仅供看板与检索 |
| 互动四数 / author_uid / author_fans / author_ip_location / keyword_match | — | 有则记，可空 | 采集侧 | 缺失时下游热度/画像用兜底值 |

> 下游入口的硬性校验只有 5 个字段（post_id、content、channel、publish_time、author_name），已核对源码；其余字段下游 adapt 层均有兜底，缺失不阻塞但降级。

### （2）口径对照表（与下游图谱侧逐项核对过）

| 项 | 我方叫法 | 对方叫法 | 是否等价 | 归一到谁 |
| --- | --- | --- | --- | --- |
| 中央权威渠道 | 监管通报 | 监管通报 | 等价（我方曾用"监管渠道"，已全量改名；参考包 12 场的旧词由对方 CHANNEL_MAP 映射，我方新数据同名直通） | 监管通报 |
| 事件编号 | event_id=13 | EVT-013（zfill 3） | 等价 | 对方格式 |

| 角色词表 | 监管/媒体/KOL/客户/网民 | LABEL_TO_ROLE 五类 | 等价，逐词命中 | 一致，无需归一 |

### （3）不一致时以谁为准

字段名、枚举值、时间格式一律以本模块交付的 28 字段格式为准；下游若出现新冲突，改下游 adapt 层的映射表，不改历史事件数据。

## 四、各阶段逐一展开

本模块实际处理阶段共 7 个（按真实流程，不套其他模块的阶段划分）：

### 阶段 1：事件参数卡（定事件）

- **做什么**：给新事件定下采集的一切前提——事件号、名称、**8 类事件类型归属**（枚举强制）、Day0 日期、主体与产品别名、检索词、排除词。
- **输入**：待采事件线索（一条可信的最早曝光帖及其链接/截图）。
- **输出**：参数卡（`event_id / event_name / event_type / start_date / end_date / subject / aliases / keywords / exclude_words` 九项）。
- **失败分支**：检索词设计不当 → 召回不足或无关噪音（以"无关泛内容"过滤兜底）；Day0 拿不准 → 标"暂定"并在采集中回溯，找到更早帖则更新 t0 并重查两天窗口。

### 阶段 2：渠道检索与候选召回

- **做什么**：只在 6 类渠道内逐平台检索，每平台记录查询词、查询时间、结果数；命中候选即打开原帖详情页，保存可直达 URL、页面标题、发布时间与正文全文（原文快照，一帖一个 .txt）。
- **输入**：参数卡 + 平台登录态。
- **输出**：候选帖集合 + 原文快照目录 + 查询记录。
- **失败分支**：平台无法检索（如抖音/小红书/黑猫投诉无日期筛选，EVT-013 补采实测）→ 记录缺口说明，不强行收录；原帖不可见 → 保存转述证据并标"待复核"。

### 阶段 3：相关性判定与过滤

- **做什么**：三层过滤——① 硬规则：发布时间必须在 Day0-Day1 窗口内、正文命中必选词与特征词、不命中排除词表；② LLM 二分类：给一句话事件摘要，逐帖判"是否在讨论同一具体事件"（排除同主题不同案例）；③ 垃圾信息 8 类清单（招聘 / 营销广告 / 撞名主体 / 无有效内容 / 重复 / 无关泛内容 / 无法核验 / 隐私）。
- **输入**：候选帖集合。
- **输出**：确认相关集合 + 待复核清单 + 排除清单（各记理由）。
- **失败分支**：拿不准的不丢（规则：只删明确命中 8 类清单的）；负面、质疑、低互动内容一律保留——它们是舆情本身。

### 阶段 4：raw 组装（21 字段）

- **做什么**：从快照读正文全文，按固定 21 字段组装，字段顺序固定、无值留 null、互动量页面不显示就留空、不臆造任何数值。
- **输入**：确认相关集合 + 快照。
- **输出**：`EVT-00N_raw.json`（+CSV 同构副本）。
- **失败分支**：publish_time 无法解析成 `YYYY-MM-DD HH:MM` → 丢弃该条并记录；channel 不在 6 类枚举 → 丢弃。

### 阶段 5：结构化与标注（build_event.py）

- **做什么**：角色判定 + 情感/主题/实体标注。
  - 角色：按序命中即停——作者名含监管关键词（12 个）或央媒白名单（19 个）→ 监管；含媒体信号词（29 个）→ 媒体；粉丝 ≥100000 → KOL；其余交给 LLM 判"作者本人是否消费者"→ 客户 / 网民（正文引语不算；LLM 不可用时黑猫投诉渠道默认客户、其余网民）。
  - 标注：LLM（DeepSeek `deepseek-v4-flash`，温度 0）产出 sentiment（正面/中性/负面）、topic_hit（只从给定主题词表选）、extract_entity（公司/产品/人物/机构名）；**情感再经口径仲裁**（标题转述标记→中性 / 标题直接定性→负面 / 客户投诉情绪→负面，见 `arbitrate_sentiment`）。
  - timespan_days = 发布日期 − t0（硬算）；is_origin = 非转载（直接从 raw 取反）。
- **输入**：`EVT-00N_raw.json` + 参数（事件号 / t0 / 话题标签 / 主题词表）。
- **输出**：`EVT-00N_processed.json`（28 字段）。
- **失败分支**：LLM 调用失败 → 自动重试 2 次，仍失败按兜底词表（14 个负面词，命中即负面、否则中性）处理并在运行结束打印失败清单；时间解析失败 → 该条 timespan_days 记 0 并打印清单；校验不过（字段缺失 / 枚举非法）→ 整体拒绝写盘。

### 阶段 6：看板生成

- **做什么**：把 processed（数据层）+ 文案包（叙事层：概述 / 时间线展示文案 / 媒体观点分组 / 传播链条节点表）合成单文件 HTML 看板。7 个模块：事件概述（含 KPI）、时间线、渠道分布（含各渠道具体平台）、情感分布与变化、关键词词云、媒体观点分类、传播链条；外加静态渠道概览与帖子明细表。
- **输入**：`EVT-00N_processed.json` + `evt_packs\EVT-00N_pack.json`。
- **输出**：`EVT-00N_舆情看板.html`（白灰配色 + 蓝色点缀 #2a78d6 仅 7 处，零外部依赖）。
- **失败分支**：文案包缺失 → 生成中止（叙事层必须逐事件精修，不能数据硬凑）；数据为空 → 图表显示 0，链条模块缺节点。

### 阶段 7：历史数据转入（事件 1-12 从参考包转换）

- **做什么**：把参考包 12 场数据（raw 27 字段 / event 30 字段，Day0-Day8）转换为当前格式：只留 Day0-Day1；raw 删 8 字段增 2 字段（→21）；processed 删 4 字段增 2 字段（→28）；渠道"监管渠道"改名并按新口径重分类；author_fans 转整数；时间补 `00:00`；event_type 替换为六大类标签。
- **输入**：《众安舆情_采集与复现包.zip》Day0-Day1 子集（97 条）+ 各事件 A_事件包。
- **输出**：EVT-001~012 的 raw / processed（与 EVT-013 同构）。
- **失败分支**：该场无 A_事件包 → event_type 留空串；域名无法映射 → source_platform 用作者名/渠道名兜底。

## 五、关键决策的依据

| # | 定了什么 | 为什么 | 代价 | 依据分级 |
| --- | --- | --- | --- | --- |
| 1 | 采集窗口只取 Day0-Day1 两天 | 下游仿真做推演只需要事件最开始的这两天数据（t0 注入窗口），事件 1-13 全部按此执行（105 条实测） | Day2 之后的发酵/衰退期内容不进数据，仿真无法观察后续演化 | 拍板（下游需求口径） |
| 2 | 渠道只认 6 类枚举 | 与下游图谱侧槽位矩阵（15 格 = 6 渠道 × 5 角色）逐字对齐 | 雪球、股吧、知乎、头条等平台不收录 | 拍板（口径） |
| 3 | 监管通报 = 中央发文级（中央部委/监管机构官方渠道 + 党央媒官方渠道） | 与下游 slots.json「监管只有监管通报一格」对齐；参考包 33 条"监管渠道"帖普查证实这是唯一词表缺口 | 公司官方公告被移出该渠道，暂无处安放（未定） | 拍板（口径） |
| 4 | 标注放 processed，raw 只存采集原值 | raw 保持"只写观察到的值"，与下游参考包"raw 透传标注"做法分道，避免采集与推断混层 | 重跑标注不可复现（LLM 无缓存，两次运行同一帖可能得到不同角色判定，EVT-013 实测出现过） | 拍板 |

## 七、与「教科书做法」的差别 + 已知边界

| 教科书/常规做法 | 本模块现状 |
| --- | --- |
| 平台官方 API 全量采集 | **无**。人工 + AI 辅助检索，样本有限、不可声称全量（平台 API 配置项仍为空） |
| 保留评论区数据 | **无**。评论字段整体删除，仅保留评论数计数 |
| 舆情生命周期四阶段（曝光/发酵/高潮/衰退）字段 | **无**。event_trend 不产出——下游不消费，参考包中仅用于采集侧趋势图，而本模块看板按 7 模块要求不含趋势曲线模块 |
| LLM 标注结果缓存、重跑可复现 | **无**。标注现场调用、无缓存，重跑结果可能有波动（温度 0 已尽量稳定） |
| 全平台历史回溯 | **部分缺口**。抖音/小红书/黑猫投诉平台无日期筛选，2019 年历史窗口无法回溯（EVT-013 补采实测，见该事件字段说明的缺口清单） |
| 采集记录全自动留痕 | **部分**。有原文快照与 post_id 映射表，但查询日志未结构化入库 |

**已知缺陷 / 没做的事**（正文对应位置已回指）：

1. LLM 标注不可复现（见阶段 5、决策 4）——未做缓存层，待办。
2. 平台 API 接入未完成（见本节表）——待用户提供接口参数。
3. 公司官方公告在 6 渠道口径中暂无归属（见决策 3）——口径未定。
4. 事件 1-12 的主题与实体标注沿用参考包结果（见阶段 7）——情感已按统一口径复标并写回（见第八节），两批数据的主题/实体标注来源存在历史差异（事件 13 为现场标注，事件 1-12 为参考包透传标注）。
5. 抖音/小红书/黑猫的历史窗口缺口（见阶段 2）——平台能力限制，无法在本模块内解决。
6. ~~负面识别准确率/召回率、情感三分类准确率未评测~~——已补齐：105 条全量评测，口径仲裁后三分类 100%、负面准确率 100%、负面召回率 100%；裸 LLM 初标为 85.71%（见第八节与《情感识别评测报告.md》）。待办：玩梗/反讽识别仍是裸模型误差源（3/105），新事件建议保留边界帖人工抽检。
